# 03 — 品質コントラクトと証拠の仕様

## 1. 目的

自律開発が陥りやすい「テストを走らせたから完成」「レビュアーが褒めたから完成」「見ていない画面を完成扱い」を防ぐ。条件は初期状態`UNVERIFIED`（未達扱い）。`PASS`へ進めるのは、現在の成果物に一致する検証の証拠が揃った場合だけ。

## 2. 受け入れ条件の例

```json
{
  "id": "FEATURE-001",
  "requirement_refs": ["REQ-001"],
  "title": "新規画面を表示できる",
  "kind": "behavior",
  "critical": true,
  "verification": {
    "commands": ["npm run test", "npm run build"],
    "scenarios": ["起動して画面を開き、指定操作後の状態を確認"]
  },
  "status": "UNVERIFIED",
  "evidence_refs": []
}
```

上記は概念例。Codexは必須・任意フィールド、バージョン、検証者、タイムスタンプ、成果物の指紋、検査の種類を含む正式JSON Schemaを作成し、無効レコード・重複ID・欠落要件・不正状態遷移を拒否する。

## 3. 証拠の鮮度

- コード・設定・アセットを対象とした指紋（ファイル内容ハッシュの規則的な集合）を記録する。未コミット変更を無視する`git rev-parse HEAD`だけでは不十分。
- テスト実行日時、コマンド、終了コード、必要ならログ抜粋、実行環境、検査対象の指紋を結びつける。
- 現在のコード指紋が証拠と違うときは、影響範囲の再検証を要求する。V1では判定が曖昧なら保守的に再検証する。
- 失敗や未実行をまとめて除外して「成功率100%」とする実装をしない。
- 機械検証結果はスクリプトで算出し、エージェントがフラグを書いただけではPASSとしない。AIレビュアーの判定は独立した証拠の一つとして扱う。

## 4. 実機検証プロファイル

### Webアプリ

実際のサーバーを起動→ブラウザで開く→主要な操作・画面遷移・入力・例外を確認→スクリーンショットとコンソールエラーを記録。UI変更がある場合、ビルド成功だけでは終了しない。

### ゲーム（2D/3D）

実際のプレイを行い、開始、移動、操作、目的達成/失敗、リスタート、視覚的一貫性、進行不能、必要な性能指標を確認する。画面検査が可能な環境ではスクリーンショット・短い操作記録を保存し、設計したゲーム体験と照合する。視覚的な完成度や面白さは単一の自動テストでは保証できないため、判定根拠と残存する人間確認の有無を明確にする。

### バックエンド/API

契約テスト、データの状態遷移、エラー処理、認証、必要な互換性、エンドポイントの実呼び出しを検査する。

### 実行環境が不十分な場合

ブラウザ、GPU、シミュレータ、ネットワーク、資格情報が不足しているなら代替を検討。それでもできない場合は`UNVERIFIED`または`BLOCKED`。スクリーンショットを生成しただけで操作テスト済みと主張しない。

## 5. 品質判定の独立性

- 実装したHaiku自身は最終承認しない。
- Sonnetレビュアーは元要求と成果物を読み、独立したコンテキストで検査する。
- 検証担当も実際のツール結果・画面を確認し、できなかった操作を列挙する。
- Opus節目監査は全体の要求未達・品質低下・抜け落ちた要件を見つける。
- 最終`verify`コマンドは、人間が再実行可能な機械判定のJSONと読みやすい概要を出す。

## 6. 終了条件

自動側の最終ゲートは：
1. 必須受け入れ条件の欠落0件。
2. すべての必須条件に現在のコードに対応した証拠がある。
3. 必須テスト、ビルド、対象プロファイルの動作チェックがPASS。
4. 独立レビューの未解決重大指摘0件。
5. 長期計画と元要求との差分をOpusが監査済み。
6. 人間に委ねる判断は分離表示され、全自動の完成と混同していない。

`/goal`側はこの機械的ゲートの実際の実行結果を会話に出してから完了判定を受ける。評価モデル単独の「達成したと思う」は完了証拠にしない。

## 7. 共通ハーネスの検証

プログラム自身に、正常系だけでなく故障注入テストを作る。未検証要件、テスト失敗、古い証拠、不正JSON、意図的なレビュー指摘、モデルの誤選択、途中中断、二重起動、権限不足、UI未確認のケースをPASSにしないことを確認する。テスト結果自体も記録し、取り込みOSSのデモ実装を無検証で信頼しない。
