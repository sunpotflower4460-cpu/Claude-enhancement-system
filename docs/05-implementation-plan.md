# 05 — Codex向け実装ロードマップと受け入れ試験

## 原則

Codex 6.1-sol（高推論）で、小さな実装→テスト→レビュー→修正を繰り返す。指示書だけ増えて動かない状態を避けるため、各フェーズは動く成果物と証拠で終える。計画は必要に応じて更新してよいが、`docs/00-requirements.md`の要求を無断で縮小しない。

## フェーズ0：前提機能のスモークテスト【最優先】

対象：最小テストリポジトリを用いた、Claude Codeクラウドの2リポジトリ選択とモデル分担の実証。

- [ ] `/goal`の利用可否、実際の継続・中断・再開を確認。
- [ ] Dynamic Workflowを利用可能か確認し、簡単な2段階スクリプトが実行できる。
- [ ] 共通リポジトリのスクリプトを選択先クラウド環境から直接呼べるか確認。
- [ ] `claude-opus-5-5`、`claude-sonnet-5-5`、`claude-haiku-5-5`をそれぞれ指定し、実際のモデルを観察。
- [ ] クラウドから読める追加リポジトリ・ファイル・エージェントの境界を記録。
- [ ] 初期設定中に新たな`.claude/agents`を置いても再起動なしで使えるかを実測。
- [ ] 初期操作が1回に収まらない場合、その理由と最も短い実用的代替手段を確定。

成果物：`docs/feasibility-report.md`（検証日時、環境/バージョン、手順、出力、成功/失敗、設計への影響）。クラウドの実測ができない実行環境では未検証とし、検証待ちを明示したまま他フェーズを進める。

## フェーズ1：状態・スキーマ・判定器

- [ ] 対象リポジトリの`.autodev/`を初期化する冪等処理。
- [ ] mission/backlog/current-task/evidenceの正式JSON Schemaと型・状態遷移の検証。
- [ ] 元の要求の保護、初期バックログ生成、既存の設定ファイルと衝突しない合成。
- [ ] リポジトリ区別用識別子と、書き込み対象の明示的な検査。
- [ ] `doctor`と`verify` CLI。成功/失敗/未検証/保留を区別。
- [ ] 証拠の現在性の確認（Git HEADだけでなく未コミット内容を含めたファイル指紋）。

終了条件：フィクスチャで正常入力、欠落、不正状態遷移、重複ID、古い証拠、対象誤認、設定衝突を自動テスト済み。

## フェーズ2：最小の実行ループ

- [ ] Sonnet planner、Haiku builder、Sonnet reviewer/verifierのエージェント定義。
- [ ] 1つの小さな機能を計画→実装→レビュー→検証→修正する`develop-sprint`。
- [ ] 各段階を構造化出力にし、途中の`null`・エラー・失敗を成功と扱わない。
- [ ] レビュアーは独立コンテキストで動かし、書き込み禁止を確認。
- [ ] 同一テスト失敗の検出とSonnetへの原因調査・実装昇格。

終了条件：わざとバグを含めたミニプロジェクトをHaikuが修正し、独立レビューとテストを経てのみPASSになる。

## フェーズ3：Opus計画・マイルストーン

- [ ] Opus architectにユーザー設計から長期計画を作らせ、元要求の対応表を保存。
- [ ] 重要区切りでOpus auditorに要求漏れ・技術負債・設計逸脱・進捗を検査させる。
- [ ] 長期計画の更新履歴とバックログの参照整合性を保つ。
- [ ] 失敗が続いた際の再計画、障害下での独立タスク継続、正直な停止判定。

終了条件：意図的に1つの要件を落としたフィクスチャでOpus監査が未達を指摘し、次のタスクへ戻れる。

## フェーズ4：実機・品質の検証

- [ ] Webゲーム/APIのプロファイルを実装し、対象から選択可能にする。
- [ ] 実行可能なブラウザ/アプリでは画面表示、主要操作、例外、必要な品質項目を検証。
- [ ] 環境が無い場合の`UNVERIFIED`と、失敗した場合の`FAIL`を区別。
- [ ] コード変更後の証拠無効化、重大レビュー未解決の完成拒否。
- [ ] 最終`verify`が機械用JSONと人間向けレポートを出す。

終了条件：ビルド成功でも画面が壊れたフィクスチャを最終完了として認めない。

## フェーズ5：初期設定と配布

- [ ] `START.md`と`bootstrap`の実働化。2つのリポジトリから対象を自動判別。
- [ ] クラウド版でプラグインを必要としない経路を整える。
- [ ] 必要なら最小の`.claude`アダプタを対象へ適用し、既存設定を保護。
- [ ] ローカルCLIで`--plugin-dir`からagents/skills/workflowsを発見可能にする。
- [ ] 一度の初期指示、進捗監視、再開の手順をユーザー向け文書へ反映。

終了条件：新しい対象リポジトリに対して同じ共通リポジトリを再利用し、手作業で設定ファイルをコピーせず開始できること。

## フェーズ6：総合確認・仕上げ

- [ ] フェーズ0〜5の機械テスト全件を再実行。
- [ ] クラウド実機で初期からの一連のテストを行う。
- [ ] 小規模Web、既存プロジェクトへの変更、簡単なゲームの3種類で追試。
- [ ] 中断後の再開、失敗からの復帰、モデルの誤ルーティング、二重起動を確認。
- [ ] 過剰なトークン消費と冗長な並列化の削減、未使用依存の整理、README更新。
- [ ] 設計とのトレーサビリティ、残課題、構築した機能の実証状況を報告。

## 必須の受け入れテスト一覧

| ID | シナリオ | 合格条件 |
| --- | --- | --- |
| T01 | 共通+対象の2リポジトリを選択 | 対象以外に書き込まず初期化 |
| T02 | 初回の`/goal`付き指示 | 予定スプリントが手動追撃なしに進行（環境許諾は除く） |
| T03 | 明示的なモデルルーティング | Opus/Sonnet/Haikuを実際に確認 |
| T04 | 意図的なコードバグ | レビュー/テストが検出し修正へ戻る |
| T05 | 古い/欠落した証拠 | 完成ゲートが`UNVERIFIED`を返す |
| T06 | ビルドPASS・UI失敗 | 完成ゲートはPASSにしない |
| T07 | 要件をバックログから削除 | 元要求との照合により失敗 |
| T08 | 同じ修正の連続失敗 | Sonnet原因調査/必要時Opus再計画 |
| T09 | セッション/Workflow中断 | 二重実装を避け、状態から再開 |
| T10 | 既存`.claude/`を持つ対象 | 上書き・破壊なしに導入 |
| T11 | 使えないモデル/ツール | 黙って代替成功とせず制約を報告 |
| T12 | 別の種類の開発対象 | 同一共通基盤を再利用できる |

### 合格の記録

各Txxは、試験日、ツール/モデル/バージョン、入力、実行コマンド、ログまたは画像の証拠、結果、未検証理由を付けて記録する。「コードを読んだ」「テストを書いた」だけでは試験合格としない。

## 完了報告の出し方

- 実装済みの段階とコミット/PR。
- 実際に走らせた受け入れテストと結果。
- クラウド／ローカルのどちらで証明されたか。
- 未実装・未検証・環境制約。
- 人間に必要な最低限の操作と、そのまま使える開始指示。

最初から完全自律で動くと決めつけず、各工程の証拠が揃った時点でV1完成とする。
