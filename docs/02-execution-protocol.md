# 02 — 自律開発実行プロトコル

v0.2の実装契約は[coordinator action定義](../skills/start-development/coordinator.md)と[06-usage.md](06-usage.md)。親rootのtask_id=missionとsprint_task_idを区別し、run/attempt/選択task executionを保存する。CLI nextとWorkflowは構造化resume(stage/task/operation)を共有する。最終検証の失敗も該当taskをresetして実装へ戻す。burst上限は未達のまま親へ返し、progress.jsonの監査間隔は次burstへ引き継ぐ。

## 1. 実行原則

「毎回モデルに自由に任せる」だけではなく、単一スプリントの進行・結果・次状態を構造化して管理する。長期計画はOpus、直近計画はSonnet、標準実装はHaiku、独立評価はSonnet、節目監査はOpusに分離。文章上のロールプレイではなく、別のモデル呼び出しとして実行する。

## 2. ステートマシン

```text
BOOTSTRAP
  -> BASELINE_CHECK
  -> ARCHITECTURE_PLAN
  -> SELECT_SPRINT
  -> SPRINT_CONTRACT
  -> IMPLEMENT
  -> REVIEW
  -> VERIFY
  -> GATE
     PASS -> COMMIT_CHECKPOINT -> [MILESTONE_AUDIT if due] -> NEXT_SPRINT
     FAIL -> FIX_PLAN -> IMPLEMENT / REVIEW / VERIFY
     UNVERIFIED -> ATTEMPT_VERIFICATION or record blocker
     BLOCKED -> work on independent tasks / stop with exact reason
  -> FINAL_AUDIT
  -> COMPLETE | READY_FOR_HUMAN_REVIEW | BLOCKED
```

段階の遷移は`backlog.json`と`current-task.json`へ書き、重複実行を避ける。検証が失敗したのに次工程へ進む分岐を作らない。Write系のagentは原則直列とし、独立した読み取り・調査・レビューだけを並列化可能とする。

### Workflowの結果と実行状態

- 各実行に`run_id`、`task_id`、`attempt_id`、期待する開始指紋を付与する。更新前に対象repo・branch・worktreeと現在の状態を照合する。
- `agent()`の`null`、エラー、schema不一致、タイムアウト、権限拒否はその段階のPASSではない。`pipeline()`/`parallel()`の配列で`.filter(Boolean)`等により失敗位置を捨てない。
- Workflowはバックグラウンドで動く。親は実行中ステージを成功と誤認せず、同一`task_id`を再投入する前に稼働中の処理を確認する。
- スクリプト本体はshell・ファイル操作・モジュール読込不可。状態読み書き、テスト、Git確認は権限を持つagentに実行させ、書き込み完了後の実状態を確認してから後続に渡す。

## 3. 初期の長期計画：Opus

- 元の設計を全文で把握し、保留点と合理的な仮定を区別する。
- ユーザーの願い・特徴・品質目標・非機能要件を失わずに成果物へ分解する。
- 大きなフェーズ、依存関係、検証可能な成果条件、マイルストーンを記録する。
- 重大な技術選択の理由を残す。細かい実装は実測後に変更可能とする。
- 初回の設計が実現困難であれば、必要な調査を行い、原案を保持したまま代替案を作る。

## 4. スプリント契約：Sonnet

次の1つまたは少数の独立した機能を選び、実装者とレビュアーが同じ「合格」を目指すように契約を固める。

最低項目：`id`、対象要件のID、事前状態、予定変更箇所、期待する動作、検証コマンド、手動相当の操作手順、未解決の前提、優先度。大きすぎる工程は小さく分割する。ユーザーの原案を改変しない。

## 5. Haiku実装とSonnetレビュー

1. Haikuに対象スプリントと実装対象だけを渡す。実装と必要なテストを追加する。
2. Sonnetレビューは別コンテキストで実施し、当初の要求・変更差分・テスト出力を調査する。レビュアーは原則読み取り専用。
3. レビュー出力は`PASS / NEEDS_FIX / BLOCKED`、重大度、問題の根拠、再現・修正方法のJSON。
4. 機械的な検証と実機検証はレビューから独立した工程にする。再現不能な指摘は不確実性を記録する。
5. 修正はHaikuに戻し、修正後は新しいコード状態について再レビューする。

レビュー役の実際のツール許可は**Read/Grep/Glob等に限定**し、Edit/Writeや無制限のBash、書き込み可能なMCP、別agentへの書き込み委任を含めない。テスト実行は別のverifierが行い、結果をレビュアーへ渡す。単にプロンプトに「読み取り専用」と書くことでは権限分離にならない。

## 6. 難航時のエスカレーション

- 同じ種類の失敗が2巡したら、Sonnetが根本原因を調査し、単純な同一パッチ繰り返しを止める。
- 独立した修正案でも失敗が続く、又は設計変更が必要ならOpusに再評価させる。
- Haikuが難しい実装で継続的に失敗する場合、Sonnet実装に変更可能。変更理由を記録する。
- 権限、利用上限、モデル未提供、環境故障などはコードのバグとして無限に修正しない。回復手段を試し、不可なら`BLOCKED`を記録し別の独立作業へ進む。
- 無限に続けること自体を目的にしない。各試行が新しい証拠・修正・計画のいずれかを生まなければ再計画または停止する。
- 目標未達を都合よくCOMPLETEへ変更しない。無進展の連続回数、実行回数、消費量は可視化し、復帰可能な保留やユーザー判断待ちとして扱う。任意の節約目標で原要求を削除しない。

## 7. マイルストーン監査：Opus

フェーズの完了、重要な技術選択の確定、大きな要件変更、繰り返す品質未達で呼び出す。監査対象は元要求、長期計画、完了済み一覧、未完了一覧、差分と実証された品質。足りない機能を既存機能で代用して完成扱いしない。新たな計画を短期プランナーへ渡す。

## 8. 中断・再開

毎スプリント終了時：`backlog`、`current-task`、`handoff`、最新の証拠参照を更新し、必要に応じてGitでチェックポイントを残す。再開時はセッション履歴だけではなく、この状態と現状コードを再検証する。

Claude Codeは停止・再開時に完了済みagent結果を再利用する場合と、途中以降のagentを再実行する場合があり、**途中で加えたファイル変更は残り得る**。再開処理は「新しいプロセスだから未実施」と推定しない。実行記録・差分・直前の検査指紋を比較し、既に適用した変更を二重適用せず、必要な場合だけ復旧する。`current-task`の更新が不完全でもコードの実状態を先に観察する。

- 実装済みだがレビュー前：レビューから再開する。
- レビュー後にコード変更あり：レビュー・検証の鮮度を再確認する。
- API失敗やワークフロー中断：再実行前にGit差分と実行記録を照合する。
- `/goal`の状態が失われた：記録した完成条件から再設定するが、過去の達成を証拠なしに引き継がない。
- Workflowがバックグラウンド中：親セッションは同一作業のワークフローを重複起動しない。完了または停止結果を待つ。

## 9. 最終出力

実装した機能・動作環境・実行した検査・実際のPASS/FAIL/UNVERIFIED・未完了項目・必要な人間確認・Gitコミットを簡潔に表示。成果が期待品質に到達していない場合は、テストが緑でも完成報告を出さない。

最終判定の直前に「進行中/不明状態のWorkflowがない」「Opus最終監査後の変更も鮮度確認済み」「最終の機械的`verify`を現在の作業ツリーへ再実行」の3点を確認する。`/goal`評価器は会話だけを読むため、この実測結果を会話にも出す。
