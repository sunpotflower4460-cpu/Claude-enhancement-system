# 00 — 製品要求とスコープ

状態：設計確定候補 v0.1 / 2026-10-25。実装・実機実証は未着手。

## 1. 何を完成させるか

Claude Codeにユーザーが「この設計のものを完成させたい」と渡したら、以後は合理的に自走できる工程を自動実行し、ユーザーが判断しなければならない内容以外はできる限り質問せずに進める。

毎回、Claude Codeのクラウドセッションで **開発対象リポジトリと Claude-enhancement-system の2リポジトリ**を選択し、基本は初回に一度だけ指示を送る。ユーザーは作業途中の状態を読め、必要に応じて介入できる。

## 2. 要件（優先度順）

- R01: 2つのリポジトリと `START.md` を用いる、再利用可能な初期化。対象リポジトリを誤認せず、設定を上書きしない。
- R02: Opus 5.5で最初の長期計画と完成条件、Sonnet 5.5で短期計画、Haiku 5.5で実装、Sonnet 5.5で独立レビューと検証、Opus 5.5で節目の監査。
- R03: レビュー指摘が残るときは修正に戻り、合格時だけ次の実装へ進む。
- R04: `/goal` とDynamic Workflowsを組み合わせ、途中経過の会話返答だけでループを終わらせない。
- R05: 元の要求を保存し、未完了の要件を見落とさず、証拠のない完了宣言を防ぐ。
- R06: ビルド・テストだけでなく、実行中のUI/操作/ゲーム体験など対象に適した検証を行う。環境上できない検査は未検証と表示する。
- R07: 作業の途中・完了・失敗・保留・理由・次の一手を対象リポジトリに残し、中断後も再開しやすくする。
- R08: 難しい工程では実装モデルをSonnetに上げるなど、固定的なモデル分担より品質を優先する。
- R09: Webアプリ、ゲーム、API/バックエンドから始め、対象に適した品質プロファイルを初期化時に選ぶ。
- R10: セットアップ失敗、モデル未提供、プラグイン/ワークフロー未対応、利用制限、手動判断待ちを正直に判別して報告する。

## 3. 想定利用者フロー

1. クラウド版Claude Codeで対象GitHubリポジトリと本リポジトリを選ぶ。
2. 設計書を対象リポジトリに置くか、最初の指示で渡す。
3. `/goal` 付きの開始指示で `START.md` を読ませる。
4. 環境診断→Opus設計→Sonnet短期計画→Haiku実装→Sonnetレビュー・実行検証→修正・次工程→Opus節目監査。
5. 機械的に検証可能な項目は証拠を残す。人間の判断が必要なら保留として明示する。

## 4. 完了状態の意味

- `PASS`: 現在のコードに対応する実証済みの条件。
- `FAIL`: 実行した検証が失敗した、または独立レビューで未解決の欠陥が見つかった。
- `UNVERIFIED`: 未実行、実行不能、証拠不足または古い証拠。
- `BLOCKED`: 外部判断・資格情報・環境等によって当該工程が進まない。
- `READY_FOR_HUMAN_REVIEW`: 自動で確認できる条件は合格したが、主観的な最終承認などが残る。
- `COMPLETE`: ユーザーが定義した完了条件に照らし、必要な検査が揃った状態。単なる実装終了ではない。

## 5. V1で行わないこと

- Development系との統合、複数社のコーディングエージェントを横断する管理、常駐OS的なサービス。
- 独自の有料バックエンド、複雑な管理画面、無関係な他リポジトリの監査。
- すべての主観的品質を完全に自動採点できるという保証。
- Claude Code側の仕様や利用制限を回避すること。

## 6. 設計上の重要方針

達成すべき成果は固定し、達成方法は必要に応じて変える。ユーザーが与えた設計をAIの判断で勝手に縮小しない。追加提案は原案と区別して記録する。実装体制の成熟より「早く実際に使えること」と再現性を優先する。
